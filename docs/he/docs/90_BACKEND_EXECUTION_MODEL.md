# מודל ריצה לבקאנד

## סטאק יעד (מומלץ)
- **Firebase Auth** לזהות (שם משתמש+סיסמה + אימות טלפון; Google; Apple)
- **Firestore** לנתוני המוצר
- **Cloud Functions (דור 2)** לכל פעולות ה־**mutation** (כתיבה)
- הלקוח קורא מ־Firestore (עם Rules קשוחות), וכותב דרך Functions בלבד.

## למה המודל הזה
- מאפשר אכיפה שרתית של חוקים: ולידציה, Rate limits, hooks למודרציה.
- Rules פשוטות יותר ומגבילות יותר.
- מוכנות פרודקשן.

## זרימות מרכזיות

### 1) עליית אפליקציה
1. בדיקת מצב התחברות מקומי.
2. אם מחובר: טעינת `users/{uid}` + `profiles/{uid}` (או מסמך מאוחד).
3. אם פרופיל חסר: “Profile Wizard” חובה (onboarding קשיח).

### 2) יצירה/עריכת פרופיל
- הלקוח שולח ProfileDraft ל־`functions/profileUpsert`.
- השרת:
  - מאמת ID token
  - בודק שדות (אורך/תווים/שדות בלתי־ניתנים לשינוי)
  - כותב `users/{uid}` ושדות נגזרים
  - רושם audit ואפשרות לדגלים למודרציה.

### 3) כניסה לצ'אט הדיפולט
- הלקוח קורא ל־`functions/chatEnsureLobbySession` כדי:
  - לבדוק ותק (למשל 7 ימים)
  - לוודא חברות בלובי
  - להחזיר chatId + הגדרות (למשל מדיניות שמירה).
- קריאה מהודעות מ־Firestore, שליחה דרך `functions/sendMessage`.

### 4) “סגולות” (מיידיות) מול “אדומות” (אימייל)
- שני מוצרים נפרדים:
  - צ'אט/DM = realtime stream
  - תיבת הודעות = threads/inbox (לא חייב realtime)
- השרת אוכף חסימות/דיווחים/ולידציות.

## אינווריאנטים
- `senderUid` תמיד זהה ל־uid מאומת.
- `createdAt` תמיד server timestamp.
- בדיקות חברות/נראות נעשות בשרת.
- “מנהל רואה הכל” רק בכלים פריבילגיים; לא נשלח ללקוחות.
